# T2 — MLX port and measurement report

The MLX port and bounded benchmark sweep are implemented in `mlx_port/`.
CPU parity passes for the actual d8 model and a 20-step AdamW trajectory.
The sandbox cannot import the installed Metal-backed MLX library; GPU
measurements require the coordinator's external runner. The benchmark table
and best-configuration section below distinguish completed measurements from
unavailable estimates. `results/mlx.jsonl` retains the sandbox's import failure.

## Commands for the coordinator

From the workspace root, outside the sandbox, using normal pip MLX:

```sh
.venv/bin/python -m mlx_port.bench --device gpu --smoke --output results/mlx.jsonl
.venv/bin/python -m mlx_port.bench --device gpu \
  --precisions fp32,mp,bf16 --micro-batches 1,2,4,8 \
  --compiled true --chunk-sizes 0,1024 --boundaries micro \
  --output results/mlx.jsonl
```

The second command benchmarks 24 actual d8 configurations and 4096-square
fp32/bf16 GEMMs. Each trial runs in a fresh process with a 1,200-second timeout,
five warmup steps, and 20 measured steps. It always processes the full global
batch of 64 sequences of length 1024 per optimizer update. It prints and
appends exactly one JSON row per configuration, including failures. See
`mlx_port/README.md` for the refinement sweep and full-training command.

## Numerical evidence

`mlx_port/parity_check.py` loads the actual initialized reference PyTorch CPU
fp32 state directly and executes the reference loss function extracted from
`train.py`. It uses the unmodified reference optimizer and scheduler. It also
checks the decay parameter names against the reference module-class mask.

The machine-readable proof is `results/mlx_parity.json`; per-step values are
included. The checks cover d8 at short CPU sequence lengths, d8 full-context
forward, explicit masks/positions, initial gradients, and 20 optimizer steps.
The small model additionally checks compilation, chunked CE, activation
checkpointing, micro/step evaluation boundaries, and mp/bf16 loss stability.

The benchmark computes projected training time as `9375 × mean_step_seconds`.
It measures forward-only evaluation time for full and final partial
micro-batches, scales to 1000 sequences, then adds **100 validation passes**.
Output fields distinguish train-only and train-plus-eval seconds. These are
steady-state estimates; startup, first-time compilation, data movement from
disk, reference W&B/module-RMS logging and checkpoint I/O are excluded.

The stated conventional dense-attention approximation is
`F = 6*N*B*S + 12*L*B*S²*d`, where N includes both embedding matrices,
B=64, S=1024, L=8 and d=512. This is **16.908816482304 TFLOP/update**.
Model FLOP/s is `F / seconds_per_step`. MFU divides by this machine's measured
4096³ GEMM FLOP/s in the matching precision (bf16 for mp/bf16, fp32 otherwise).
This is utilization relative to an achieved matmul roofline, not advertised
hardware peak. It counts dense masked attention work, approximates embedding
work, and excludes checkpoint recomputation in the numerator.

## Implementation and caveats

- `model.py`: MLX fast RMSNorm, split-half RoPE and causal SDPA; exact parameter
  paths and layouts allow strict loading of reference weights.
- `train_mlx.py`: `value_and_grad`, compiled differentiated micro-step and
  optimizer update, fp32 masters/moments, exact masking/bias correction/clipping
  and LR schedule. Compilation uses explicit state inputs, not captured stale
  weights. Full data training accepts pre-shuffled `.npy` files and saves final
  fp32 weights. It does not implement periodic checkpoint/resume or W&B.
- Precision flags: `fp32` throughout; `mp` bf16 linear/attention operations
  with fp32 embedding/residual/norm scale streams; `bf16` bf16 activation and
  residual streams. Both reduced-precision modes retain fp32 master weights,
  gradient accumulation and Adam state; fp32 CE in every mode. They are
  loss-safe alternatives, not claims of bit-identical autocast behavior.
- CE chunks the head projection before creating vocabulary logits and
  checkpoints chunks for backward. Chunk size 0 computes the whole head.
- `micro` evaluates accumulated gradients after each micro-batch; `step`
  materializes once per full update, retaining a potentially large lazy graph.
  Both synchronize weights/state/loss before timing the next step.
- Memory includes MLX peak allocation and macOS process peak RSS. MLX's
  working-set limit is advisory; wired memory is limited, and each process has
  a deadline. OS memory pressure can still affect throughput.
- Benchmarks use synthetic resident tokens, exercise real parameter updates,
  and check finite loss. The 20-step parity/stability checks do not establish
  full-run convergence on the unavailable training corpus.
- Historical T2 CPU validation used a separate **source-built MLX v0.32.4**, commit
  `36969c094354086e15d2a327a9c50feb20b9cf11`, under `.build/`, with
  `MLX_BUILD_METAL=OFF`. This workaround follows the
  [MLX maintainers' CPU-only build guidance](https://github.com/ml-explore/mlx/issues/3148).
  The installed Metal package is unchanged. Added build tools with
  `uv pip install -p .venv cmake ninja`: cmake 4.4.5, ninja 1.13.2.
  T5 removed this sandbox-specific build workflow. Current tests use normal
  pip MLX, with `MLX_DEVICE=cpu` to request CPU execution; an accessible Metal
  runtime may still be required during import. See the root README.
- No git commits, `.env` reads, or reference edits were performed.
