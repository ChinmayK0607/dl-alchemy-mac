## Commands

From the workspace root, run outside the sandbox:

```sh
.venv/bin/python torch_mps/bench.py --device mps --smoke --output results/torch_mps_smoke.jsonl
.venv/bin/python torch_mps/bench.py --device mps --suite recommended --roofline --output results/torch_mps.jsonl
.venv/bin/python torch_mps/report.py
```

The smoke test uses a tiny model, one warmup and two timed steps, with a 45-second child timeout. It is explicitly excluded from performance selection. The measured suite tries 29 unique training configurations plus nine bf16/fp32/fp16 4096³ matmul rooflines (three matmul precision settings). Each measured configuration first passes CPU-fp32 versus selected-device 20-step correctness, then runs the unchanged d8 recipe with ≥5 full-step warmups and ≥20 timed full steps. The full grid has four precisions × micro-batches 8/16/32/64; additional one-factor probes cover explicit-mask versus causal SDPA, compile modes, AdamW flags, matmul precision, loss layouts and head chunk sizes.

After the first sweep, use a focused Cartesian grid around the winner; for example (replace the values with measured winners):

```sh
.venv/bin/python torch_mps/bench.py --device mps --precisions bf16-autocast --micro-batches 8,16 --optimizers default,foreach,fused --compiles off,default --losses chunked,ce --matmul-precisions highest,high,medium --roofline --append
```

The benchmark synchronizes before/after timing, preloads a full random token batch on the device, uses equal micro-batch loss weights, clips once, and updates once per 64 sequences. Fresh subprocesses, a configurable 1,800-second hard timeout, and process-group termination isolate OOM/compiler/kernel failures. One JSON record is printed and saved per config, with errors preserved; CPU fallback is disabled. Use `--append` to preserve previous sweep results. Compile failures never silently become eager results.

## Projection, roofline and MFU

For N=34,612,736, B=64, T=1024, L=8, d=512, the dense-attention convention is `F_step = 6*N*B*T + 12*L*B*T^2*d = 16,908,816,482,304` FLOPs (16.908816 TFLOP/update). The attention term counts forward and backward QK/AV products over the dense square. A triangular useful-work convention halves that term; neither convention includes elementwise operations or output-head recomputation. `MFU = (F_step / seconds_per_step) / (measured matching-dtype matmul TFLOP/s × 1e12)`. This is utilization relative to an achieved square-matmul roofline, not advertised hardware peak; mixed compute is approximated by its dominant matmul dtype.

Matmuls use preallocated outputs, five warmups and at least 20 measured iterations with MPS synchronization. The harness measures bf16, fp32 and fp16 roofs, and records the float32 matmul precision setting. MFU stays unmeasured when a matching roof is absent; include `--roofline` in focused sweeps.

`projected_total_seconds = 9375*sec_per_step + 100*seconds_per_validation_pass`. Validation is measured using 20 synchronized micro-batch forwards after five warmups, with the 1000-sequence remainder timed separately. The projection includes all 100 evaluations. Throughput counts B*T input tokens, consistent with the assignment token budget, while the loss predicts B*(T−1) labels.

## Limitations

- No MPS access in this sandbox; an external tiny smoke test passed, but full-recipe GPU optimization choices remain implemented experiments, not measured wins. torch.compile, fused AdamW and precision/kernel support must be established by the external sweep.
- MPS in this PyTorch build exposes current/driver allocation counters but no public exact peak/reset counter. The harness samples both every 10 ms and also reports process high-water RSS. MPS figures are sampled lower bounds; RSS includes CPU runtime and unified memory and must not be added to MPS allocation as if disjoint.
- Synthetic batches are resident on the device and repeated. The projection excludes dataset decoding/transfers, network/W&B logging and module RMS metrics, checkpoint serialization, startup/compilation, and thermal drift over a full run. The reference saves latest checkpoints at steps 1000…9000 and at the final step, plus its completed artifact. These require separate measurements for a complete end-to-end wall-clock prediction.
- `train_mps.py --steps 9375` executes the recipe on a fixed synthetic batch. It does not implement DCLM data loading, periodic checkpoint persistence or W&B; the benchmark measures periodic evaluation separately. Long-run convergence and sustained thermal performance are unverified.
- Report generation is deterministic with respect to input records apart from its timestamp. Regenerate after the external coordinator replaces/appends GPU records; no nonexistent timing is inferred.
